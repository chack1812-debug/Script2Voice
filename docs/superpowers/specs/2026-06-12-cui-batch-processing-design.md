# CUI 複数台本バッチ処理（エンジン起動1回） 設計書

作成日: 2026-06-12

## 背景・目的

多数の台本を処理するとき、現状の CUI（`script2voice`）は **台本を1つだけ** 受け取り、
処理の最後に `shutdown_all()` でエンジンを停止する。複数台本を処理するには CUI を
台本の数だけ起動する必要があり、**台本ごとに音声合成エンジンの起動待機（AivisSpeech は
初回モデルロードに最大 60 秒）が発生**する。これがバッチ作業の最大のボトルネックになっている。

本変更では CUI を **複数台本対応** にし、1プロセスで「**エンジンを1回だけ起動 → 全台本を
暖まったまま順番に処理 → 全部終わったら停止**」というライフサイクルにする。これにより
エンジン起動コストをバッチ全体で1回に圧縮する。

### 採用しなかった案（記録）

- **全台本横断のグローバル並行パイプライン（台本をまたいで合成/音響/書き出しを交互実行）**:
  合成スループットは現状すでに **エンジン別セマフォ** で頭打ちのため、横断並行にしても
  取り分は「台本Aの書き出し中にエンジンが遊ぶわずかな隙間」を埋める程度で限界的。
  一方 `Producer` の「処理単位＝1台本」前提を作り替える大改修となり、タイムライン/書き出しの
  正しさに回帰リスクがある。**変更コスト（リスク含む）に効果が見合わない**ため見送る。
- **エンジンの分離起動（プロセス終了後も生かす永続化）**: オーフェンプロセス管理が必要になり
  リスクが増える。エンジンの寿命を**バッチ実行の範囲に閉じる**ほうが低リスクなため不採用。
  （常駐運用が必要なら、ユーザーが先にエンジンを起動しておけば既存の `is_alive()` 再利用で
  対応でき、S2V が起動していないプロセスは終了時に kill しない。コード変更不要。）

## スコープ

- **やること**
  - CUI の引数を `scripts: Vec<PathBuf>`（1個以上、ファイル/ディレクトリ混在可）に拡張する。
  - 引数展開: ファイルはそのまま、ディレクトリは直下の `*.txt` を名前順に展開、重複除去。
  - 1プロセスで全台本を処理するバッチループ。エンジンは起動1回、最後に停止1回。
  - **エラー継続**: ある台本の失敗で中断せず、全台本を処理しきってからサマリ報告。
  - **台本ごとログ**: 従来どおり各台本の `project_dir/run.log` に出力（1プロセス内で出力先を切替）。
- **やらないこと**
  - GUI 側の複数台本キュー UI（別途の後続タスク）。
  - `Producer`（`src/lib.rs`）本体の処理ロジック変更（台本内の並列処理は現状のまま再利用）。
  - 台本横断のグローバル並行パイプライン化（上記理由で不採用）。
  - エンジンの分離起動・永続化。
  - Python 版への同等変更。

## Part A — CLI 引数と展開

### 対象
`src/main.rs` の `Cli` 構造体と引数処理。

### 変更内容
- `script: PathBuf` → `scripts: Vec<PathBuf>`（clap の可変長位置引数、`num_args = 1..` 相当で
  1個以上必須）。`--config` は従来どおり。後方互換: 1個指定なら従来と同じ動作。
- 新規の自由関数 `expand_script_args(args: &[PathBuf]) -> anyhow::Result<Vec<PathBuf>>`:
  - 各引数について:
    - ディレクトリ → `read_dir` で直下の拡張子 `.txt`（大文字小文字無視）を収集し、
      **ファイル名で昇順ソート**して追加。
    - ファイル → そのまま追加。
    - 存在しない → エラー（どの引数かを含むメッセージ）。
  - 収集後、`canonicalize` した実体パスで **重複除去**（出現順は維持）。
  - 結果が 0 件ならエラー（「処理対象の台本が見つかりません」）。

### 設計判断
- 「複数パス指定」と「フォルダ一括」を**1つのインターフェースで両対応**。
  `s2v A.txt B.txt` / `s2v ./scripts` / `s2v ./scripts 追加.txt`（混在）すべて通る。
- 展開ロジックを自由関数に切り出し、後で GUI 側が複数台本を受けるときに流用できるようにする。

## Part B — バッチ実行ライフサイクル

### 対象
`src/main.rs` の `main` と `run_pipeline`。

### 変更内容
1. **引数展開**: `expand_script_args` で台本リストを確定。
2. **事前パース**: 各台本をパースし `Vec<(PathBuf, anyhow::Result<Vec<Scene>>)>` を得る。
   - パース失敗は**その台本の失敗として記録**し、以降の対象から外す（バッチは継続）。
3. **必要エンジンの和集合**: パース成功した全台本の `cast.engine_type` を集めて union を作る。
4. **エンジン起動（1回・継続的）**: union の各エンジンを **個別に** `activate()` する。
   - 1つの起動失敗で全体を中断しない（`activate_required` の fail-fast は使わない）。失敗した
     エンジンは警告ログを残し、そのエンジンを必要とする台本は後段の合成で失敗扱いになる。
   - `EngineManager::get(name)` で `Arc<dyn Engine>` を取得し `engine.activate().await` を
     順に（または `join` で並行に）呼ぶ。新規 API は追加しない。
5. **台本ごと処理**: パース成功した台本それぞれについて、既存の `Producer` を生成して
   `produce(&scenes)` を実行。出力は各台本名のフォルダ（既存の project_dir 決定ロジックを
   `process_one` として関数化して再利用）。失敗は記録して**次の台本へ継続**。
6. **停止（1回）**: 全台本処理後に `engine_manager.shutdown_all()` を呼ぶ。
   - パニック等でも停止が走るよう、処理本体を関数に閉じ、`shutdown_all()` は呼び出し側で
     必ず実行する（現状の `let result = ...; shutdown_all(); result?` と同じ構造を踏襲）。
7. **サマリ**: 成功件数／失敗件数、失敗した台本名と理由を最後にログ出力。

### エラー方針・終了コード
- **継続**: パース失敗・エンジン起動失敗・台本処理失敗のいずれも、その台本（または該当エンジン
  依存の台本）を失敗として記録するだけで、バッチ全体は最後まで続行する。
- **終了コード**: 失敗が1件でもあれば非0（`anyhow::bail!` でサマリを返す）。全件成功なら0。

### 設計判断
- 台本ごとに `Producer::new` を作り直す（`audio_dir`/`timeline` ディレクトリ作成は台本フォルダ
  単位のため）。`EngineManager` と内部の `AudioProcessor` 設定は使い回せるが、`Producer` は
  軽量なので台本ごと生成で問題ない。
- 事前パースで union を確定してからエンジンを起動するため、**使わないエンジンは起動しない**
  （現状の単数実行と同じ方針を維持）。

## Part C — ログ（台本ごと run.log の維持）

### 対象
`src/main.rs` の `init_logging`。

### 問題
現状 `init_logging(project_dir)` は `project_dir/run.log` 向けの file レイヤを含む
グローバル subscriber を `.init()` で**プロセス内に1回だけ**初期化する。バッチでは1プロセスで
複数台本を回すため、**台本ごとに subscriber を再 init できない**。

### 変更内容
- **コンソール出力**: 起動時に1回だけ初期化（従来どおり）。
- **ファイル出力**: 「現在処理中の台本の `run.log` を指す**差し替え可能な共有ハンドル**」を持つ
  カスタム `MakeWriter` を file レイヤに与える。
  - 共有状態 `Arc<Mutex<Option<std::fs::File>>>`（追記オープンしたファイル、未設定時は `None`）。
  - `MakeWriter::make_writer` はこのハンドルをロックして書き込む実装を返す。`None` のときは
    `io::sink()` 相当（どの台本にも属さないバッチ前後のログはコンソールのみ）。
  - 台本処理の直前に、その台本の `project_dir/run.log` を追記オープンして共有ハンドルに設定。
    台本終了時に `None` に戻す（またはflush）。
- バッチ前後・サマリのログはコンソールに出る（ファイルはどの台本の run.log にも混ざらない）。

### 設計判断
- 台本は**逐次**処理されるため、ファイル出力先が切り替わるのは台本の境界のみ。`Mutex<File>` で
  十分（台本内の並列タスクからの書き込みは同一ファイルへ直列化される）。
- 非ブロッキング書き込み（`tracing_appender::non_blocking`）は本方式では使わない。ログ量は
  info レベルで少なく、同期書き込みで実用上問題ない。WorkerGuard も不要になる。
  - （代替案: `tracing_subscriber::reload` で file レイヤごと差し替え、各台本に non_blocking と
    guard を割り当てれば非ブロッキングを維持できる。複雑度が上がるため初版では採らない。）

## データフロー

```
引数(Vec<PathBuf>)
  └─ expand_script_args ─> 台本パスList(重複除去・順序保持)
        └─ 各台本パース ─> [(path, Ok(scenes) | Err)]
              ├─ Err は失敗記録(継続)
              └─ Ok から必要エンジンunion算出
                    └─ union を個別 activate(失敗は警告・継続)
                          └─ 各 Ok 台本: process_one(=従来の project_dir決定 + Producer.produce)
                                ├─ 直前に run.log を共有ハンドルへ設定
                                ├─ 成功/失敗を記録(失敗でも次へ)
                                └─ 終了で run.log を外す
        └─ shutdown_all()(1回)
        └─ サマリ出力 + 失敗ありなら非0終了
```

## 影響ファイル

- `src/main.rs`
  - `Cli`: `script: PathBuf` → `scripts: Vec<PathBuf>`。
  - `expand_script_args`（新規・自由関数）。
  - `init_logging`: 差し替え可能 `MakeWriter` 方式に変更（共有ハンドルを返す/受け取る）。
  - `process_one`（新規・1台本処理を関数化: project_dir 決定 + run.log 設定 + Producer.produce）。
  - `main`: バッチループ・union 算出・継続エラー集計・サマリ・終了コード。
- 既存 `run_pipeline` は `process_one` 相当に吸収または再構成。
- `src/lib.rs`（`Producer`）: **変更なし**。
- `crates/s2v-engines/*`: **変更なし**（`Engine::activate` / `EngineManager::get` /
  `shutdown_all` を既存のまま利用）。

## テスト

- **引数展開** `expand_script_args`:
  - 単一ファイル / 複数ファイル / ディレクトリ（`.txt` のみ収集・名前順） / ファイル+ディレクトリ
    混在 / 重複指定の除去 / 存在しないパスでエラー / 0件でエラー。
  - tempdir に `.txt` と非 `.txt` を置き、収集対象とソート順を検証。
- **必要エンジン union 算出**: 複数 scenes から `engine_type` の和集合が正しく出ること。
- **バッチ継続（結合, エンジンはスタブ）**:
  - 3台本中1台本を失敗させ、**残り2台本が処理され**、サマリに失敗1件、終了コード非0になること。
  - パース失敗の台本があっても他台本が処理されること。
- 既存テスト（`resolve_config_path` 系・CLI パース）は維持。`Cli` の引数変更に合わせて
  `script` 単数前提のテストを `scripts` 複数前提に更新。

## 未決事項・リスク

- **ログの非ブロッキング廃止**: 初版は同期書き込み。実運用でログ量が問題になれば reload 方式へ。
- **エンジン起動の並行/逐次**: union が複数エンジンの場合、`activate` を並行にするかは性能の
  好みで、初版は実装が単純な逐次でも可（個別呼び出しなので後で並行化も容易）。
- **ディレクトリ展開の再帰**: 初版は**直下のみ**（サブフォルダは辿らない）。必要になれば拡張。
